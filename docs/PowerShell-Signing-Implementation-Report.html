1. Executive summary

The requested service was implemented from a fresh main baseline without using earlier script-signing memory or old branch details. It signs PowerShell source through a synchronous JSON API using Java 17, Spring Boot, Jsign, SHA-256 Authenticode, an externally supplied PKCS#12 identity, and optional RFC 3161 timestamping.

Explicit non-goals

  • Certificate issuance, renewal, or production key generation.
  • Signing formats other than PowerShell .ps1.
  • Long-term script storage, queues, or asynchronous job orchestration.
  • An identity provider inside the application; authenticated and authorized ingress is a deployment precondition.
  • HSM or remote signing in this iteration; the PKCS#12 adapter is replaceable if that becomes mandatory.

10. What SD-AI did wrong

  1. It generated insecure defaults. allow_force_approval_bypass: true, approval-free workspace writes, empty protected paths, enabled architecture waivers, and disabled workflow enforcement conflict with safe engineering governance. Publication was blocked twice.
  2. It routed to unavailable providers. Generated semantic profiles referenced Claude/Copilot/Gemini in an environment where Codex was the usable provider. Capability discovery should happen before configuration is materialized.
  3. Its deterministic output failed its own critical profile. The workflow marked steps completed even though it had not produced the RFC, contract, required diagrams, threat model, or acceptable ADR.
  4. It mislabeled a brief as implementation. The implement step completed in 34 ms and created an “AI Implementation Brief” explicitly saying it would not modify application source. Engineers could misread that as a completed implementation phase.
  5. It generated shallow placeholder content. The initial security review contained unchecked generic prompts, the plan contained generic workstream headings, and validation failure details were not represented as actionable structured findings in the audit.
  6. Its quality gate was language-inappropriate. The generated test command was pytest -q for a Java/Maven service. Codex had to replace it with ./mvnw ... clean verify.
  7. Provider readiness was superficial. The Codex process was considered ready, then emitted 179 heartbeats with no first output for 15 minutes. A first-token/handshake deadline should fail much earlier.
  8. There was no useful fallback or resume. One failed requirements agent stopped every downstream agentic phase. No bounded retry with diagnosis, fallback provider, deterministic handoff, or resume-from-next-step mechanism completed the workflow.
  9. It did not record token or cost usage. The user-requested accounting cannot be reconstructed, even for the 900-second attempt.
  10. It created diagnostic file explosion. A heartbeat every few seconds became 179 separate committed files. This is auditable but noisy, slow to publish, and unfriendly to review.
  11. It had a feature-store path inconsistency. Some newer status/analyze commands expected specs/changes/PS-SIGN-001, while the active workflow stored the feature at specs/PS-SIGN-001.
  12. It did not validate external repository capabilities. A dependency-review job was added later by Codex, but SD-AI supplied no repository-capability preflight or fallback guidance. The first CI run failed because Dependency Graph was unavailable.
Balanced assessment: SD-AI was useful as an artifact checklist, deterministic scaffold, and immutable audit recorder. It was not reliable as an autonomous agentic delivery engine in this run.
