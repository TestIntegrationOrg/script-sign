1. Executive summary

P0

Generator/validator mismatch

SD-AI can generate an architecture baseline that does not structurally satisfy its own critical architecture validation contract.

P0

Criticality conflates assurance with documentation breadth

A security-critical but architecturally small service can be forced into the maximum artifact catalog.

P1

Canonical artifact ownership is unclear

Deterministic baselines and semantic reviews overlap, making it unclear which artifact is the actual source of truth.

P1

Evidence is fragmented

Review output, plugin evidence, validation state, approvals, and worktree evidence live in different locations and formats.

Most important finding: the deterministic architecture generator and critical architecture validator are not aligned. The generator writes a smaller and differently named artifact set than the validator expects. This is a real SD-AI framework issue, not a result of the GitHub-only emulation used for this feature.

The core improvement should be to move SD-AI from a required-files model to an engineering-evidence model. The framework should determine what evidence is required from feature characteristics, then allow the minimum sufficient set of canonical artifacts to satisfy that evidence.

2. Method and important caveat

This review was produced by inspecting the SD-AI framework source and the resulting script-sign feature branch. The original implementation session did not execute sdai run end-to-end in a local workspace. The runtime lacked a local SD-AI execution environment, so the lifecycle was approximated through the GitHub connector while following SD-AI conventions.

Evaluation rule: duplicate numbered artifacts created by that approximation must not be counted as proof that SD-AI itself duplicates artifacts. Framework findings below are limited to behavior supported by the actual SD-AI source/configuration.

Primary framework areas reviewed

  • src/sdai/agents/lifecycle.py — deterministic requirement, architecture, planning, implementation-brief, and security artifact generation.
  • src/sdai/workflow_templates.py — agentic and enterprise workflow sequencing and review outputs.
  • .sdai/architecture-validation.yaml and architecture validation code — required artifact classes by lifecycle mode.
  • .sdai/agents/architect.agent.md — semantic architect responsibilities and capabilities.
  • .sdai/agents/requirements-analyst.agent.md — semantic requirements-analysis responsibilities.
  • Workflow orchestrator persistence behavior for AI review outputs and plugin evidence.

4. How SD-AI currently behaves

The enterprise workflow combines deterministic baselines, semantic AI reviews, human approvals, workspace-writing implementation, post-implementation reviews, quality gates, and validation.

Intake
  ↓
Deterministic specification baseline
  ↓
AI requirements review (advisory)
  ↓
Deterministic architecture baseline
  ↓
Parallel AI architecture + security reviews (advisory)
  ↓
Architecture approval + security approval
  ↓
Deterministic plan/tasks
  ↓
Workspace-writing implementation agent
  ↓
Parallel code review + test review
  ↓
Tests / optional Trivy / optional Sonar
  ↓
Validation

This is a sound governance concept: baseline, review, approval, implementation, evidence, validation are intentionally different lifecycle states. The usability problem is that these states are frequently represented as separate files without a sufficiently strong concept of canonical ownership and evidence consolidation.

5. Detailed findings

P0 Finding 1 — Critical lifecycle equates high assurance with maximum artifact breadth

The critical architecture profile requires a broad catalog: specification, RFC, architecture alternatives, decision matrix, ADR, C4 context, component diagram, sequence diagram, security/threat model, API/event contract, and traceability.

Why this is a problem

  • Security criticality and architectural complexity are not the same thing.
  • A small service can require strict security controls while needing only a few architectural decisions.
  • Mandatory artifact breadth creates document volume even when multiple evidence needs could be satisfied by a single well-structured document.
  • Developers can begin optimizing for validator satisfaction rather than decision quality.

Underlying model issue

Current:
criticality → required document catalog

Recommended:
feature characteristics → required engineering evidence → minimum sufficient artifacts
P0 Finding 2 — Deterministic architecture generation and validation are not contract-compatible

The deterministic architecture lifecycle creates:

architecture/architecture.md
architecture/decision-matrix.md
architecture/context.mmd
architecture/container.mmd
adr/ADR-001-initial-architecture.md

The critical validator expects artifact forms such as:

rfc/RFC-*.md
architecture/diagrams/context.*
architecture/diagrams/component*.*
architecture/diagrams/*sequence*.*
security/threat-model.md
contracts/openapi*.* (or another contract type)
tasks.yaml + specification.md traceability

Concrete mismatch examples

ConcernGeneratorValidatorImpact
Context diagramarchitecture/context.mmdarchitecture/diagrams/context.mmd or equivalentGenerated artifact may not satisfy validator by path.
Component viewarchitecture/container.mmdarchitecture/diagrams/component*.*Different architectural view and naming.
RFCNot generatedRequired for criticalCritical workflow remains incomplete.
Sequence diagramNot generated by deterministic architectRequired for criticalAdditional manual/agent materialization required.
Threat modelSeparate generic security-review.mdsecurity/threat-model.mdReview checklist and required security model are different artifacts.
API contractNot generatedRequired for criticalREST/event contracts must be produced elsewhere.
Expected invariant: artifacts produced by a deterministic lifecycle step should satisfy the structural requirements that step claims to establish, or the step should explicitly report which required evidence remains incomplete.
P1 Finding 3 — Semantic architect has the right capabilities but is advisory

The semantic architect is designed to work with RFCs, ADRs, C4 diagrams, sequence diagrams, API contracts, threat models, and traceability. This is almost exactly the set demanded by critical validation.

However, the architect runs in advisory mode. Its output is persisted as a review artifact rather than as the canonical architecture artifact set.

Resulting contradiction

Validator requires rich canonical architecture artifacts
                  ↓
Semantic architect knows how to produce them
                  ↓
Architect is advisory only
                  ↓
Review content exists, but canonical files may still be missing

This creates an avoidable materialization step and encourages duplication between “architecture” and “architecture review.”

P1 Finding 4 — Requirements baseline and requirements review overlap

The deterministic requirement agent creates generic FR/NFR/AC content intended to establish traceability. The semantic requirements analyst then performs the domain-specific work needed to create implementation-useful, testable, traceable requirements.

This can make the review artifact more useful than the canonical specification.

Risk

specification.md       → canonical, but generic
ai/requirements-review → detailed, but advisory

Question for engineer: which one should implementation trust?

A better pattern is for deterministic logic to establish structure/schema and for semantic analysis to propose changes to the canonical specification, with explicit promotion/approval.

P1 Finding 5 — Architecture baseline and architecture review overlap

The deterministic architecture baseline always proposes generic choices such as modular component, independently deployable service, and event-driven capability, plus a sample decision matrix. The semantic architect then performs another, richer architecture analysis.

This is useful as a safety mechanism but inefficient as a document model. The framework should preserve independent review without requiring two competing narrative sources.

P1 Finding 6 — Validation is artifact-oriented more than evidence-oriented

The validator mostly asks whether specific artifact classes exist and meet basic structural checks. That is deterministic and safe, but it can over-reward document count.

Current tendency

completeness ≈ required artifact types present

Desired tendency

completeness ≈ required decisions + risks + contracts + traceability + approvals covered

A single architecture document might legitimately contain context, components, alternatives, trade-offs, trust boundaries, and sequence behavior. SD-AI should be able to validate logical sections/evidence claims, not only independent files.

P1 Finding 7 — Evidence is fragmented across storage models

AI step output, plugin execution evidence, workflow state/approvals, and worktree execution evidence are not exposed through one canonical feature evidence index.

  • AI review output is saved under paths like ai/requirements-review.md and ai/code-review.md.
  • Plugin evidence uses plugin/<step>.json.
  • Worktree evidence is stored outside ordinary tracked source under Git metadata.
  • Approvals and validation status use workflow-specific state.

This makes the user question “show me all evidence for this feature” harder than it should be.

Recommended capability

Generate a machine-readable and human-readable evidence manifest that indexes all evidence without duplicating the underlying content.

P2 Finding 8 — Lifecycle terminology mixes assurance and execution strategy

SD-AI exposes concepts such as light, standard, critical, agentic, and enterprise. These are not all the same dimension.

Recommended conceptual split

Assurance level:
  light | standard | critical

Execution profile:
  individual | agentic | enterprise

Examples:
  standard + individual
  critical + agentic
  critical + enterprise

This would make governance choices more understandable and reduce accidental activation of heavyweight artifact profiles.

P2 Finding 9 — Generic deterministic prose creates boilerplate noise

Deterministic generators create safe but broad statements that are intentionally not domain-specific. When semantic agents later generate richer analysis, the generic prose remains in the repository.

Consider making deterministic outputs schema-first or placeholder-light, then promoting reviewed semantic content into canonical artifacts.

P2 Finding 10 — No strong duplicate/canonical-source detection

SD-AI should warn if competing artifacts exist for the same logical role, for example both 01-specification.md and specification.md, or multiple architecture narratives with no explicit relationship.

This would have caught the duplication introduced during the GitHub-only emulation and prevented users from confusing it with framework output.

6. What is not an SD-AI defect in this case

The following should not be used as evidence against SD-AI because they were introduced during the connector-only implementation workflow.
  • The coexistence of 01-specification.md and specification.md.
  • The coexistence of 02-architecture.md and architecture/architecture.md.
  • The coexistence of 03-security.md and security-review.md.
  • The manually created repository-visible evidence/ directory.
  • Any implication that a real local sdai run produced the manually written evidence summaries.

These are still useful examples for designing duplicate detection and evidence packaging, but they are not proof of native SD-AI duplication behavior.

8. Recommended target model

8.1 Replace “required files” with “required engineering evidence”

Feature intake
   ↓
Feature characteristic classification
   ↓
Required evidence profile
   ↓
Minimum sufficient artifact plan
   ↓
Canonical artifact generation/refinement
   ↓
Independent review
   ↓
Human approval where required
   ↓
Implementation + tests
   ↓
Evidence manifest + validation

8.2 Example feature characteristics

CharacteristicEvidence implication
REST APIRequire versioned OpenAPI contract.
Asynchronous eventsRequire AsyncAPI/event schema; otherwise do not require it.
Persistent dataRequire data model, retention, migration, and recovery evidence.
Security-sensitive trust boundaryRequire threat model and security approval.
External provider dependencyRequire integration contract, failure modes, timeout/retry assumptions.
Material technology choiceRequire ADR.
Multiple deployablesRequire component/container deployment view.
Complex runtime interactionRequire sequence diagram.
Simple single-service interactionAllow sequence section in architecture doc instead of mandatory separate diagram if policy permits.

8.3 Introduce canonical artifact ownership

Each logical artifact role should have exactly one canonical source. Reviews should reference it, propose patches, or produce findings against it.

Canonical:
  specification.md
  architecture/architecture.md
  contracts/openapi.yaml
  security/threat-model.md
  tasks.yaml

Review/evidence:
  reviews/requirements.json
  reviews/architecture.json
  reviews/security.json
  evidence/manifest.json

The review artifact should not become a competing source of business or architecture truth.

8.4 Add evidence manifest

A generated manifest could provide one index:

{
  "feature": "SIGN-001",
  "assurance": "critical",
  "execution_profile": "enterprise",
  "evidence": [
    {"id":"requirements", "artifact":"specification.md", "status":"approved"},
    {"id":"api-contract", "artifact":"contracts/openapi.yaml", "status":"validated"},
    {"id":"threat-model", "artifact":"security/threat-model.md", "status":"approved"},
    {"id":"tests", "source":"quality-gate:tests", "status":"passed"}
  ]
}

The manifest should index evidence, not duplicate it.

10. Acceptance tests for future SD-AI improvements

These tests can be used as framework-level acceptance criteria when changes are implemented later.

AT-01 — Generated baseline is structurally valid

Given a new feature and a selected evidence profile, when SD-AI runs deterministic baseline generation, then every artifact claimed as generated must satisfy the same path/type schema used by validation.

AT-02 — Critical small service does not receive irrelevant artifacts

Given a security-critical synchronous REST service with no events and no database, then SD-AI must not require AsyncAPI/event artifacts or data-model artifacts solely because the assurance level is critical.

AT-03 — REST contract is required when REST is present

Given a feature exposing a REST endpoint, then a versioned OpenAPI contract must be part of the required evidence set.

AT-04 — Review does not create a competing source of truth

Given an AI requirements or architecture review, then domain changes are represented as findings or a proposed canonical patch; the review output is not treated as a second approved specification or architecture.

AT-05 — Evidence can be queried from one index

Given a partially or fully executed workflow, then a single command or manifest lists every required evidence item, producer, artifact/source, current status, approval state, and blocking reason.

AT-06 — Duplicate role detection

Given both 01-specification.md and canonical specification.md, then SD-AI warns that multiple files appear to claim the specification role and identifies the configured canonical artifact.

AT-07 — Waiver is semantic, not a shortcut

Given a required evidence class that is genuinely not applicable, then SD-AI records structured N/A rationale and approval where policy requires it; it must not generate a meaningless placeholder document merely to pass validation.

AT-08 — Review independence remains intact

Given canonical artifacts generated or edited by an implementation-capable agent, then architecture/security review must remain an independent step with separate findings and approval status.

AT-09 — Re-running a lifecycle is idempotent

Given an existing feature with canonical artifacts, when a deterministic or semantic lifecycle step is re-run, then SD-AI updates or reviews the configured canonical artifact instead of creating a second naming convention.

AT-10 — Artifact count is not the success metric

Given one architecture document that contains all required logical evidence sections allowed by policy, then validation can succeed without requiring artificial splitting into multiple markdown files.

The objective is not to make SD-AI less rigorous. The objective is to make rigor proportional, traceable, and evidence-driven so that a critical service receives strong security and approval controls without automatically receiving every possible architecture document.

12. Suggested SD-AI implementation roadmap

Phase 1 — Fix internal contracts

  1. Create one shared artifact-role registry/schema used by scaffold, generators, semantic agents, and validators.
  2. Make deterministic generator paths exactly match the configured canonical paths.
  3. Add framework tests proving generated baseline artifacts are recognized by validation.
  4. Add duplicate-role warnings.

Phase 2 — Introduce evidence profiles

  1. Separate assurance level from execution profile.
  2. Classify feature characteristics such as REST, events, persistence, external provider, security boundary, multiple deployables.
  3. Resolve characteristics into logical evidence requirements.
  4. Support structured N/A/waiver rationale for genuinely irrelevant evidence.

Phase 3 — Canonical artifact promotion

  1. Represent semantic review output as findings and proposed edits against canonical artifacts.
  2. Add approval/promote semantics rather than creating parallel authoritative narratives.
  3. Make reruns idempotent.

Phase 4 — Evidence consolidation

  1. Add evidence/manifest.json generated from actual workflow state.
  2. Add optional human-readable evidence/summary.md generated from the manifest.
  3. Index test gates, review findings, approvals, plugin evidence, worktree evidence, and validation results without copying their content.
  4. Add a command such as sdai evidence SIGN-001 to answer completeness and blockers.

Phase 5 — Artifact coalescing and policy sophistication

  1. Allow policy to state that one artifact can satisfy multiple logical evidence classes.
  2. Validate required headings/claims/relationships rather than only independent paths.
  3. Keep strict file separation available for organizations that want it.

13. Review checklist

Use this checklist when deciding which SD-AI improvements to implement first.

  • Does a deterministic generator produce artifacts the validator recognizes?
  • Can critical assurance be selected without automatically requiring irrelevant artifact classes?
  • Is there exactly one canonical specification and one canonical architecture source for a feature?
  • Can AI reviews improve canonical artifacts without becoming competing sources of truth?
  • Can a user identify all blocking evidence from one command or manifest?
  • Can a non-applicable artifact be explicitly justified instead of replaced by boilerplate?
  • Can small features coalesce logical evidence into fewer files while maintaining rigorous validation?
  • Are assurance level and execution/governance profile configured independently?
  • Does rerunning SD-AI avoid duplicate artifacts?
  • Are review, approval, implementation, and test responsibilities still independently auditable?
